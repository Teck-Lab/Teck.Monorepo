# Confirmed subscription event contract

Billing publishes `SharedKernel.Events.SubscriptionPaymentConfirmedIntegrationEvent` only after a trustworthy captured-payment outcome or privileged external-invoice verification is committed. Stub provider responses are not evidence of a real charge; they MUST NOT be represented as real card processing.

Consumers (license and provisioner) MUST deduplicate by `SubscriptionId`, treat `TenantId` as the global Customer registry GUID, and use the immutable snapshot fields rather than re-resolving the mutable quote. The event carries `SourceOrderId`, `PlanId`, `PlanVersion`, `AmountMinor`, `Currency`, `DatabaseStrategy`, `DatabaseProvider`, `HasReadReplicas`, `ReplicaCount`, `PaymentMethod`, `ConfirmedAtUtc`, `ValidFromUtc`, and `ValidUntilUtc`. `PaymentMethod` is `captured` or `external_invoice`; the latter is permitted only after privileged, audited invoice verification.

Customer correlates the event by Customer registry `TenantId`, canonical slug, `SourceOrderId`, and `SubscriptionId`; mismatched reservations are rejected. The paid event is **not** a readiness signal. The Customer status remains `paid_pending_readiness` while Keycloak owner membership, license, or database readiness is missing. Keycloak generates a distinct organization GUID, persisted on the Customer tenant; token organization IDs must resolve through Customer to the canonical registry GUID, and inactive tenants return no database routing. `TenantProvisioningReadyIntegrationEvent` must correlate both subscription and order and originate from the actual licensing/database provisioners before the tenant can become active.

Cancellation publishes Billing-signed `SubscriptionAccessSuspendedIntegrationEvent` with the immutable order, subscription, and Customer tenant IDs. Customer immediately clears its readiness gates. Licensing verifies Billing's public key, records a permanent subscription-keyed PostgreSQL suspension tombstone, and revokes any already-issued license in the same transaction. A delayed paid event cannot issue another license after the tombstone; concurrent issuance and suspension serialize on the subscription key. Neither an unsigned cancellation nor a replay with a different order or tenant can revoke a license. Billing's Stripe confirmation, invoice confirmation, and cancellation handlers use explicit Wolverine EF `[Transactional]` middleware so the aggregate change and outgoing event enter the same durable outbox transaction.

`TenantProvisioningReadyIntegrationEvent` currently carries `TenantId`, `SourceOrderId`, `SubscriptionId`, and `Provisioner` (`license` or `database`). Customer rejects missing, stale, or mismatched order/subscription IDs before recording readiness; duplicate matching readiness remains idempotent after activation. Correlation alone does **not** authenticate the producer. License and database producers must provide trusted, observable evidence before this event is used to grant access; publishing arbitrary messages with correct IDs is not an authorization mechanism.
