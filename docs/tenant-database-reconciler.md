# Tenant database reconciler contract

`TenantDatabase.Host` is an executable polling worker. Its Wolverine handlers accept only Billing RSA-verified paid and suspension events. A PostgreSQL request row records the current paid source order, predecessor and desired state; a changed replay is rejected. The worker publishes a database-only HMAC-signed readiness event bound to that source order and the healthy CNPG Cluster UID after every service migration and application-role login succeeds. Publication is retried until the PostgreSQL row acknowledges it. Do not insert desired state from an unauthenticated caller or treat a healthy Cluster alone as tenant readiness. For paid backup or HA, readiness additionally requires the observed Barman WAL plugin, an operator-observed active ScheduledBackup, and ready synchronous standby instances; an accepted manifest is not proof that a backup has completed or recovery works.

Only paid dedicated PostgreSQL tenants belong in the reconciler-managed `tenant-databases` namespace. Tenant resource names derive from the Customer registry UUID, never a caller-supplied slug. The existing `postgres` namespace cluster belongs to Argo/GitOps and must never be modified. The durable desired-state snapshot retains Billing's independent `HasScheduledBackups` and `HasHighAvailability` entitlements alongside read-replica count, including across paid-period renewal. Provisioning creates a tenant-isolated Barman `ObjectStore` and enables the CNPG plugin WAL archiver for every tenant to support the baseline final backup; only the separately purchased scheduled-backup add-on creates a daily plugin `ScheduledBackup`. HA adds one synchronous standby independently of purchased read replicas; the operator must report all instances ready before entitlement readiness. Configure `TenantDatabase:Barman:DestinationPath` as an S3 bucket/prefix ending in `/`, `TenantDatabase:Barman:CredentialsSecret` as the namespaced Secret containing `ACCESS_KEY_ID` and `ACCESS_SECRET_KEY`, and optional `TenantDatabase:Barman:EndpointUrl`. The worker fails closed without these settings. Namespace-scoped ServiceAccount permissions, the worker image/deployment, CNPG 1.30 and compatible Barman plugin, object-store credentials and OpenBao policy belong to Teck.GitOps #7; they have not been deployed.
The durable request also stores the verified paid-period end and effective grace/backup-retention days from the same signed Billing snapshot. A suspension preserves these terms and does not extend Customer, gateway, or Licensing authorization beyond the paid end. The verified `renewal_failed` reason is stored separately from cancellation. Only a retained failed-renewal row with a recorded healthy source Cluster UID wakes after the signed paid end plus its grace period; the worker leases it, takes the tenant/order advisory lock, and requests an idempotent, order-and-Cluster-UID-fenced on-demand Barman plugin `Backup`. An absent UID, cancellation, or prior-order replay cannot enter that path. Creation is not proof of completion, archived WAL, or a successful disposable restore; the due row retries at a bounded interval, and verified recovery, hibernation, and automatic erasure remain unimplemented. A separate read-only PostgreSQL selector now reports automatic expiry eligibility only for retained dedicated tenants with `renewal_failed`, a stored Cluster UID, positive trusted grace and recovery-retention terms, and no explicit-purge state. Its exact deadline is `PaidUntilUtc + GracePeriodDays + BackupRetentionDays`, so signed enterprise overrides are honored; each result includes the current source order, Billing proof, predecessor, tenant identifier, and Cluster UID and must pass a tenant-advisory-lock recheck against the current row before caller work. This is eligibility only: it performs no deletion, is not an approval, and does not invoke the explicit CSI verifier. Automatic Barman restore verification, complete object-store erasure, CNPG/PVC/secret cleanup and absence checks, and disposable real-operator recovery/erasure proof remain required before destructive polling can be enabled. Destructive purge polling stays disabled. If a Cluster is hibernated, only a paid successor of its current source order may atomically set `cnpg.io/hibernation=off` during an order-fenced reconciliation; this guard is not a substitute for verified recovery or the missing hibernation lifecycle.

An operator-attached enterprise policy is delivered as a separate Billing-attested transition after the active paid order exists, not as a mutated replay of the immutable payment event. Customer and tenant-database consumers verify Billing and Licensing signatures, bind the transition to the current tenant, subscription, and source order, and query Licensing for the current ACTIVE document before attaching terms. A revoked, superseded, unavailable or mismatched document fails closed. The tenant-database store accepts exact replay idempotently and rejects a conflicting transition. Automatic nonpayment purge is still disabled: the current expiry selector uses persisted terms but does not refresh Licensing status again at the retention deadline.

The focused `TenantK3sManifestTests` integration test uses Testcontainers.K3s with pinned CNPG 1.30.1 and Barman Cloud plugin 0.15.1 CRDs to submit and retrieve actual Kubernetes `ObjectStore`, `Cluster`, `ScheduledBackup`, and final plugin `Backup` resources. It runs agentless because this API-only schema test does not run Postgres; Docker privileged-container capability is required. It proves Kubernetes API acceptance, not operator reconciliation, actual Barman WAL persistence, restoration, or erasure.

An in-cluster SeaweedFS S3 acceptance test is currently blocked in the supported Docker sandbox: K3s with its agent enabled exits because `/dev/kmsg` is absent. A diagnostic run verified that a disposable privileged K3s container can start when `/dev/kmsg` is created inside its isolated container, and its node reports `Ready`; however, this environment's pod networking blocks container egress to the Kubernetes API needed for kubelet exec probes, so a SeaweedFS pod is not Ready. Garage remains the passing S3 compatibility test until a schedulable K3s environment can run the real SeaweedFS pod.

The focused `TenantGarageObjectStoreTests` uses a disposable Testcontainers Garage 2.4.1 single-node S3 store. It proves representative base-backup and WAL keys under one tenant prefix can be written and read, then deleted without deleting another tenant's key. A standalone archive-erasure primitive uses S3 `ListObjectVersions` to enumerate versions and delete markers under the exact tenant prefix, rejects off-prefix keys and missing version IDs, deletes bounded batches, and confirms absence. Synthetic S3 transport tests exercise pagination, isolation and failures; Garage 2.4.1 returns `Unimplemented` for version listing, so it cannot prove that primitive against a real object store. Neither test runs the CNPG operator, Barman plugin or a PostgreSQL restore, and neither authorizes hibernation or automatic erasure. The primitive is not registered with the automatic purge poller.

Before a Customer-approved database purge, the worker must acquire Billing's durable exclusive purge fence for the exact tenant, subscription, paid order and approval. It holds the grant through independent restore verification and CNPG deletion; any denied or unavailable request keeps deletion disabled, and the grant is completed only after deletion succeeds. Configure `BillingPurgeFenceClient:TokenEndpoint`, `ClientId`, `ClientSecret`, `Scope` (including `billing:purge-fence`) and `BillingBaseUrl` with the dedicated `tenant-database-worker` service account; never reuse the `billing-api` identity. Billing requires audience `billing-api`, claim `billing_purge_worker_identity=tenant-database-worker` and scope `billing:purge-fence`. These credentials and the realm permission are readiness prerequisites. An interrupted verification or deletion retains the durable exclusive gate and must resume the same grant before retrying.

A dedicated tenant has separate `basket`, `catalog`, `inventory`, `order` and `pricing` databases. Each service Host runs its own `--migrate` Kubernetes Job using its image; a Complete Job is not enough without verification that the current paid period's application role can authenticate and read its owned schema. The worker publishes verified application connections under `/tenants/{tenantIdentifier}/{serviceName}` in OpenBao KV v2 with source-order compare-and-set. Customer and Billing remain global. Every new paid period retains the subscription ID but receives a distinct Billing order, ten new period-specific migration/application role Secrets and a fresh readiness cycle. The previous paid order cannot re-enable a suspended Cluster or overwrite its successor's OpenBao connection.

`TenantDatabase.Host` owns one central PostgreSQL worker database containing only the durable `tenant_database_requests` queue and its purge request/approval fields. It is not an owner or migrator of tenant schemas: tenant databases remain governed by each tenant service deployment; this worker orchestrates their provisioning and readiness checks.

Provision the worker database schema as an explicit deployment step by running the host with `--migrate` against its required `ConnectionStrings:TenantDatabaseWrite` central worker database before starting the polling worker; there is no fallback to another service's `Default` database. Normal host startup does not apply migrations; readiness remains unhealthy until the queue exists. The migration adopts a compatible pre-existing SQL-created request table without replacing or deleting retained requests or approvals, and rejects incompatible shapes rather than recording the migration. Keep this central database in the operations group alongside the `tenant-database` worker and reconciler.

CNPG creates a tenant-scoped manager role during bootstrap with `CREATEROLE` and `pg_signal_backend`, using PostgreSQL ADMIN grants without inherited application privileges or `SET ROLE`. The manager Secret remains worker-only. On signed cancellation, Customer immediately denies routing; the database worker serializes paid-order advancement and suspension with a PostgreSQL tenant advisory lock. Kubernetes JSON Patch resourceVersion and source-order tests reject stale Cluster updates. CNPG managed service roles are reconciled to `NOLOGIN` with `disablePassword: true`; the manager also sets all eleven service/bootstrap roles to `NOLOGIN PASSWORD NULL`, terminates their sessions and verifies no remaining logins. The worker then writes source-order-bound OpenBao tombstones, soft-deletes superseded credential versions, and removes the ten former role Secrets and five migration Job connection Secrets. `Retained` is not recorded until these steps succeed; failures remain retryable. A signed successor can restore access only with new role Secrets and renewed migration/readiness checks. Kubernetes Secret presence alone never proves revocation.

Retention expiry never deletes data by itself. Customer exposes `POST /tenants/{tenantId}/purge-approvals` on its dedicated Keycloak `customer:purge` permission: two different `platform-manager` subjects must separately approve the same currently suspended, paid dedicated tenant after `PurgeApproval:RecoveryDays`. Customer stores immutable per-operator approval rows and signs the second decision with its own encrypted `PurgeApproval:EncryptedPrivateKey` and `PurgeApproval:Passphrase`, separate from Billing's payment key. Its transactional outbox publishes the signed source-order, subscription, tenant, suspension and recovery-window snapshot. The worker trusts only `PurgeApproval:TrustedPublicKeys`, enforces its **own** positive `PurgeApproval:RecoveryDays`, and persists the accepted decision for asynchronous retry. Its local lock rejects a wrong tenant/order or a newer paid period already delivered to the worker; it does **not** fence a Billing-paid period whose event remains in transit.

The current purge prototype requires a previously healthy Cluster UID, a suspended source-order Cluster, a configured `TenantDatabase:VolumeSnapshotClass` with `snapshotOwnerReference: none`, and a CNPG on-demand `volumeSnapshot` Backup matching the Cluster UID/order. It restores that Backup to a separate one-instance Cluster and probes all five recovered databases over verified PostgreSQL TLS before recording the Backup and restored Cluster UIDs. Kubernetes UID/resourceVersion-preconditioned deletes then target the temporary Cluster, five tenant Database CRs and original tenant Cluster. Billing now serializes payable/pending orders and paid confirmations against a durable exclusive purge grant, rejecting a stale Customer projection and denying all future orders after a completed grant. **Do not enable destructive purge yet:** a Backup resource UID alone cannot protect its backing snapshots from concurrent loss. A reviewed, independently protected and recoverable snapshot retention policy, worker deployment, and staging validation are still required before deleting a source Cluster. A completed Backup CR or fake Kubernetes test alone does not prove retained recovery.

Teck.GitOps #7 still needs the worker image/Deployment, namespace-scoped RBAC for tenant Clusters/Databases/Backups/Secrets/Jobs, NetworkPolicy allowing Keycloak/OpenBao/tenant PostgreSQL, Customer purge-key distribution, reviewed CSI `VolumeSnapshotClass`/storage retention policy and a mounted PostgreSQL CA. Do not use or modify the Argo-owned `postgres` namespace Cluster. A disposable kind Kubernetes 1.36.4 cluster with CNPG 1.28.4 and the CSI hostpath test driver completed a `volumeSnapshot` Backup with a `Retain` snapshot content, restored a separate Cluster, queried all five databases, then retained the ready snapshot and restored data after deleting the source Cluster. The first restore attempt exposed a CNPG-generated snapshot recovery Job name exceeding the 63-character DNS-label limit; the worker now uses `restore-{tenantId:N}`. This local test does **not** establish protected, immutable or offsite production snapshot retention, nor exercise the worker's authenticated in-cluster Kubernetes/verified PostgreSQL TLS path or Argo sync. Automatic purge remains disabled until protected production recovery is independently proven; no production destructive rollout or completed delivery is claimed.
